# 增量 PRD：响应式布局与本周订单导出

> 项目：星期衣精致洗衣衣物照片系统（Electron 33 + Vue 3 桌面端）
> 仓库路径：`E:\软件开发\星期衣精致洗衣衣物照片系统`
> 文档类型：增量 PRD（仅描述本次变更，不复述整个系统）
> 版本：v1.0（草稿）｜编写人：许清楚（产品经理）｜语言：简体中文

---

## 1. 产品目标

让「星期衣精致洗衣衣物照片系统」在门店实际使用的各种显示器（1366×768 老机到 3440×1440 带鱼屏、100%/125%/150% DPI 缩放）上都能铺满可用空间而非甩出右侧空白带，让拍照取景区按屏幕可用空间放大且画面完整不变形，并让本周订单页从「只能看」升级为「能按当前筛选条件导出成 Excel 可直接打开的表格」——三处改动都不新增角色与权限模型，全部建立在现有的窗口层（main.js）、样式层（renderer/styles.css）、取景状态机（renderer/camera-controller.js）与导出管道（main/store.js `exportPhotosByDate`）之上。

## 2. 需求背景与动机

| 需求 | 为什么现在做（一句话） | 现状证据 |
|---|---|---|

## 3. 用户故事

1. 作为**拍照账号**，我希望取景区占据页面主要宽度并按窗口比例放大，以便在小屏老机上也能看清衣物污渍与吊牌细节、一次拍准。
2. 作为**拍照账号**，我希望摄像头不可用时不只弹出一行小字，而是明确告诉我「是权限被拒 / 被别的程序占用 / 根本没插设备 / 初始化超时」并给出对应按钮，以便我能自助恢复而不必打电话给维护方。
3. 作为**拍照账号**，我希望在 1366×768 的门店机器上不需要滚动就能同时看到完整取景区和「拍照」「释放摄像头」按钮，以便连续扫码连拍不被打断。
4. 作为**门店管理员**，我希望本周订单页能按「条码关键词 / 录入人 / 门店 / 日期」筛选，以便快速定位某个店员或某个条码负责的订单。
5. 作为**门店管理员**，我希望筛选后点一个按钮就能把当前结果导出成表格交给洗衣管家或财务，以便不再手工抄写条码与张数。
6. 作为**门店管理员**，我希望导出的表格双击即可用 Excel 打开且中文表头不乱码、条码不被显示成科学计数法式的怪值，以便交给不太懂电脑的同事也能直接用。
7. 作为**系统管理员**，我希望导出内容包含全部订单字段（备注、录入人、门店、时间、照片位置），以便跨门店对账与追溯时不需回系统再查一遍。
8. 作为**任意角色（含查询账号）**，我希望我把窗口拖到 3440×1440 带鱼屏或把系统 DPI 调到 150% 后，弹窗、面板、表格都自动等比适配且不会跑出屏幕或被裁切，以便不必每次都手动拖窗口。

### 4.3 需求三：本周订单导出

**「当前筛选条件」的定义**：本周订单页的筛选为**前端本地过滤**（页面已在 `load()` 中把近 7 天全量记录拉到内存，见 `renderer/renderer.js:4988-5000`），筛选条件 = 「近 7 天（含今天）」∩「页面上各筛选控件当前值」。导出的数据集必须与页面上可见的表格行**逐一一致**（同一份 `filteredRows`）。

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| R3-1 | **筛选能力**：新增筛选条，包含 ① 关键词（匹配条码 / 录入人 / 门店 / 备注，不区分大小写）；② 录入人下拉（来源：当前结果集的 `users` 集合）；③ 门店下拉（仅当可见门店 >1 时显示）；④ 日期（在近 7 天内再收窄到某一天或自定义区间）；⑤ 「重置筛选」按钮 | P1 | ① 关键词输入某条码 → 表格行数 == 1，且该行条码等于关键词；② 选择录入人 A → 所有行的「录入人」文本包含 A；③ 选择门店 B → 所有行门店 = B；④ 叠加 ②③④ 后行数 == 手工计算结果；⑤ 点「重置」后行数回到全量 `rows.length`；⑥ 汇总文案（`共 N 个订单 · M 张照片`）随筛选同步变化；⑦ 所有筛选控件在 `loading=true` 时禁用 |

## 8. 关键决策与取舍

### D1｜内容区是否完全取消 `max-width:1440px`？

- **推荐：完全取消，容器一律铺满；仅「固定数量卡片集合」允许元素级 `max-width:480px` 左对齐。**
  理由：用户抱怨的是**窗口右侧整条空白带**（≥1920 时 240px、3440 时 1760px），只有取消上限才根除；把上限改为「居中 + 更宽的容器」只是把右留白分成左右两条，问题没解决。卡片集合允许元素级留白是因为它们是「信息块」而非「工作区」，贸然拉伸到 1000px 反而降低可读性。
- 放弃选项 A：保留上限但改为 `min(可用宽, 1920)` 居中 —— 代价：1440–1920 之间仍有小留白，且违背用户明确诉求。
- 放弃选项 B：完全不限、卡片也跟着拉伸 —— 代价：3440 屏上统计卡变成 1000px 宽的「面条」，门店人员读数困难。
- 副作用缓解：超宽带来的富余宽度由**拍照取景区（R2）**与**本周订单表新增备注列 / 更宽列宽（R3）**消化。

### D2｜弹窗尺寸怎么放大：`clamp()` 比例缩放 vs 按断点分档 vs 全屏

- **推荐：`clamp(最小值, vw比例, 最大值)` 为主 + `.modal-sm` 分档兜底。**
  理由：一条 CSS 覆盖全部中间态，无需维护多个断点；`clamp` 的下界保证 1024 最小窗口下不塌成细条，上界保证在 3440 屏上不会变成超过 1600px 的巨型对话框（信息密度不足）。
- 放弃选项 A：按 1366/1920/2560 三档 media query —— 代价：断点之间的窗口尺寸仍是固定值，且需维护三套规则。
- 放弃选项 B：所有弹窗统一 `width: 88vw` —— 代价：确认框/改码框这类 2 行的弹窗会被拉成巨宽，视觉失衡，且遮罩点击区变大导致误关。

### D3｜导出通道：复用 `exportPhotosByDate` vs 新增专用通道 vs 渲染层生成 CSV

- **推荐：新增专用通道（如 `records:exportWeeklyOrders`），并把 CSV 写出抽成 `store.js` 内的共用函数 `writeCsv()` 与 `exportPhotosByDate` 复用。**
  理由：① `exportPhotosByDate` 已身兼「复制照片」与「仅表格」两职，再加「前端筛选 + 8/9 列 + 明细模式」会让参数膨胀并与两个既有调用方（按日期导出照片、导出当日订单表格）形成回归耦合；② 专用通道能精确产出 payload（`dateFrom/dateTo/barcodes/mode`）并给出精确的日志动作名；③ 与本周订单页语义 1:1，未来「任意筛选导出」可复用同一入口。
- 放弃选项 A：扩展 `exportPhotosByDate` 参数 —— 代价：语义含混（同时接受日期与条码列表），且不得不改动两个稳定调用方，回归面更大。
- **放弃选项 B：渲染层用 Blob 直接生成并下载 CSV** —— 代价：违反本项目「所有数据出口走主进程」的既有契约（contextIsolation 下渲染层无写文件能力），且绕过权限裁剪、不产生操作日志、服务端模式拿不到数据。此项为架构红线，不接受。

### D4｜聚合导出 vs 明细导出 vs 两者都给

- **推荐：两者都给，默认聚合、可切明细。**
  理由：门店日常场景是「本周接了多少单、每单几张」→ 聚合，且与页面所见完全一致（WYSIWYG，降低培训成本）；客服/洗衣管家需要「某一张照片什么时候拍的、文件名叫什么」→ 明细。二者共用同一份数据集，实现成本增量约 20 行。
- 放弃「仅聚合」：出现照片缺失/重复争议时无法追溯到单张文件名，只能回系统查。
- 放弃「仅明细」：门店最常核对的是订单与张数；明细行数通常是订单数的 3–10 倍，Excel 里反而不便汇总。

### D5｜长数字条码在 Excel 中显示为科学计数法

- **推荐：保持 RFC4180 纯数据（不做 `="123456789012"` 之类的技巧），在导出成功 toast/提示文案中给出「若条码显示为科学计数法，请将该列设为文本」的指引。**
  理由：导出文件的消费方包含程序化解析（洗衣管家上传助手），任何 `="…"` 公式包装都会污染数据。
- 放弃选项：导出时对超 11 位纯数字自动加 `="…"` —— 代价：文件内容不再是纯数据，下游解析失败风险不可控，违背「可直接用 Excel 打开」之外的二次利用需求。

### D6｜拍照页在 1366 屏是否改为单列堆叠

- **推荐：是，断点暂定 `(max-width:1439px) or (max-height:820px)`，具体阈值由架构师实测微调。**
  理由：1366 占门店老机比例高，双栏下取景区只有约 730px；改单列后可到约 1078px，直接满足「主要比例」诉求，而「拍照」「释放摄像头」按钮所在的 `.camera-bar` 仍在取景区正下方，连拍动线不变。
- 放弃保持双栏：老机上本次需求等于没做。
- 代价：1366 屏上「备注输入」「保存」等次要控件需要向下滚动才能看到 —— 缓解措施是保持 `.camera-bar` 与条码输入区在首屏（R2-5）。
