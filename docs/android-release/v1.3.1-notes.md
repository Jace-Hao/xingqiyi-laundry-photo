# v1.3.1 发布说明

> **性质**：移动端修复版本。桌面端（Windows 安装包）代码无任何改动，**无需重新安装桌面端**，
> 仍兼容 v1.3.0 及以上服务端。

## 修复的问题

安装 v1.3.0 **正式包**后，「测试连接」报错：

> 已连接到 192.168.110.10:17521，但对方返回的不是本系统的数据。
> 对方实际返回：`{"ok":true,"data":{"app":"xingqiyi-laundry-photo","apiVersion":2,"features":{...}}}`

响应体完全合法、服务器也正常，但 App 判定失败——**这是安装包自身的缺陷，不是地址或端口问题。**

## 根因

`proguard-rules.pro` 中 Gson 数据模型的保留规则写错了包名：

```
-keep class com.xingqiyi.laundryphoto.data.remote.** { *; }
```

而**全部 Gson DTO 都在 `data.model`**（`Models.kt` / `Role.kt`），
`data.remote` 只放 Retrofit 接口与 OkHttp 拦截器，**一个 DTO 都没有**。
这条规则保护了空目录，放过了真正需要保护的地方。

正式包开启代码压缩后，R8 判定 DTO 字段无人引用并全部剥离：

| 检查项 | v1.3.0 正式包 | v1.3.1 正式包 |
|---|---|---|
| `CapabilitiesDto` 访问标志 | `PUBLIC ABSTRACT`（空壳） | `PUBLIC FINAL`（正常） |
| 实例字段数 | 0 | 齐备 |
| dex 中 `"apiVersion"` 字符串 | 0 次 | 11 次 |

Gson 反射实例化零字段抽象类时抛出：

```
JsonIOException: Abstract classes can't be instantiated!
Adjust the R8 configuration or register an InstanceCreator or a TypeAdapter
```

而 `JsonIOException` **是 `JsonParseException` 的子类**，恰好命中 `ApiClient.translate()`
的 `is JsonParseException ->` 分支，被翻译成「对方返回的不是本系统的数据」，
于是把发布包缺陷伪装成用户的地址 / 端口 / 桌面端版本问题。

## 改动内容

1. **`android/app/proguard-rules.pro`** — 补上 `data.model.**` 与 `data.local.**`（Room 实体同样按字段名序列化）的保留规则
2. **`ApiClient.kt`** — 将 `JsonIOException` 的判断提到 `JsonParseException` **之前**，
   新增 `clientSideDefectMessage()`。客户端缺陷与「服务端返回非 JSON」是两回事，
   合并成一个分支会让真实根因被永久掩盖；今后同类问题会直接说明「本 App 安装包存在缺陷」
3. **新增 `ProguardKeepRuleTest`**（6 条用例）— 断言 DTO 包被显式保留、且字段名与服务端键名一致

> 这类问题单元测试测不出来（测试跑的是未压缩代码），`assembleRelease` 也不会报错
> （R8 剥离字段是合法行为），只有真机正式包会崩。因此新增守卫测试在构建期拦截。

## 安装与验证

1. **卸载手机上的旧版本**（debug 与 release 签名不同，无法直接覆盖安装）
2. 安装 `xingqiyi-laundry-photo-android-v1.3.1-release.apk`
3. 填写 `http://内网IP:17521` → 点「测试连接」

**预期**：显示「连接成功，服务端版本 v1.3.0」。
