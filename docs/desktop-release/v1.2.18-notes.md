# 桌面端 v1.2.18 发布说明

**一句话**：修「v1.2.17 升级后预览整片白屏」——彻底移除给预览 `<video>` 套的 SVG 滤镜，改用**相机原生亮度参数（brightness）在 ISP 层压暗**，预览与成片同源；同时修掉亮度档三处会导致真机完全失效的生产级缺陷。

| 项目 | 值 |
|---|---|
| 版本 | v1.2.18 |
| 配套 | 移动端无需联动升级（独立版本号） |
| 上一版 | v1.2.17 |
| 建议 | **v1.2.17 必须升级**——该版本在部分机器上预览整片白屏，等于相机不可用 |

---

## 一、这个版本解决了什么问题

### 首要：v1.2.17 的白屏（阻断级，必须升级）

v1.2.17 为让「预览与成片同源」给预览 `<video>` 套了 SVG `feComponentTransfer` 滤镜（`#xqy-exposure-lut`）。在 Electron / Chromium 下，**对视频元素施加 SVG 滤镜会让它的硬件合成层渲染挂掉**，画面不再显示、露出白色容器 —— 整片白屏。

本版本**彻底移除该滤镜**：预览 `<video>` 不再绑定任何后期 `:style` 滤镜，源码里也不再保留那段滤镜定义（有回归断言守着，防止再被加回来）。

### 压暗改走相机原生亮度参数（ISP 层）

预览不再做后期处理，改为通过 `track.applyConstraints({advanced:[{brightness}]})` 下发**相机原生亮度参数**：

- 压暗发生在 **ISP 层**，预览与成片**天然同源**，所见即所得；
- 不再有任何后期 LUT / 滤镜，不存在滤镜合成层的白屏风险；
- 亮度参数是**加性黑电平偏移**，比手动曝光轻、**不会触发画面崩塌**。

**档位顺序**（从轻到重）：曝光补偿 → **原生亮度 → 手动曝光 → 软件兜底**。某档被实测判无效会自动降到下一档。

### 顺带修掉亮度档的三处生产级缺陷

现场真机跑起来后暴露出三个必须修的问题（都会让功能**完全失效**或**反复空转**）：

1. **模块级纯函数引用了闭包变量** —— 每次下发亮度约束都抛 `ReferenceError`，曝光辅助**整条链路失效**。现改为显式传参，不传时退回默认值。
2. **字符串档的档位判定错误** —— `'brightness' > 0` 恒为 `false`，凡是用数值比较判断「是不是硬件档」的地方，亮度档都被静默误判成「软件兜底」，导致：幽灵打击**记不进记忆**、降级链**直接掉底**、零调整安全网**失效**。现统一由档位判定函数（`tierRank`）与记忆键归一化函数（`expGhostKey`）裁决。
3. **降级链原地打转** —— 每次降级只摘掉当前档的能力，探测空间没缩小，会在「曝光补偿 → 亮度 → 曝光补偿」之间循环。现改为**跨调用累积**已失效能力键，探测空间单调收缩，必然收敛。

另外修了一处映射口径：满量程参照原先用整个量程（max−min），而基线在量程中点时实际能下压的空间只有一半，会导致码值直接撞到量程底部（ISP 余量被吃光、压到极值出现色偏/噪声）。现按**实际可用下行空间**（base−min）计算。

## 二、门店会观察到的变化

- 预览**不再白屏**，画面正常显示；
- 黑色衣物过曝时：预览与照片**同时变暗**，白垫板仍是白、黑衣仍有纹理层次，**不蒙灰**；
- 画面稳定，**不来回跳亮度**；
- 浅色衣物、正常设备：行为与 v1.2.17 一致，无感；
- 这一切都是自动的，**不需要任何操作**，覆盖安装即可。

重点验收（问题设备）：

1. 打开相机 → 预览**正常显示，不是白屏**；
2. 黑色皮衣放上 → 预览与照片**变暗且褶皱/口袋纹理可见**；
3. 白色垫板放上 → **白板仍是白，不蒙灰**；
4. 画面稳定、**不来回跳**，预览亮度与成片一致；
5. 把衣物拿走 → 约 3 秒后徽标消失、画面恢复正常。

## 三、排查用日志

| 日志事件 / 字段 | 含义 | 怎么判 |
|---|---|---|
| `CAM_EXP_ENUM` 的 `tier` | 实际选中的档位 | `brightness` = 原生亮度档；`0` = 软件兜底；`1` = 曝光补偿；`2` = 手动曝光 |
| `CAM_EXP_STEP` | 每步压暗调整 | 看 `ev` 与 `subjectMean` 是否平稳收敛；亮度档的码值应逐档变低 |
| `CAM_EXP_FALLBACK{reason:'ghost-remembered'}` | 该档位在此设备上已被实测判无效，本次直接跳过 | 连续出现说明这台设备的该路径确实无效 |
| `CAM_EXP_FALLBACK{reason:'comp-ineffective'}` | 当前档无效、已降到下一档 | `from` / `tier` 字段可看出降级路径 |
| `CAM_EXP_OVERPRESS` | 设备实际压得比请求更深 | 徽标据实显示其 `actualEv` |

若仍有异常，请把 `CAM_*` 日志导给我们。
