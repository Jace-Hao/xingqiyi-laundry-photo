## 一、这个版本解决了什么问题

v1.2.14 之后，门店反馈「循环跳亮度、自动调节过暗」**依然存在**。这次拿到了问题设备的全天日志，统计出一个关键数字：手动曝光档一天里介入了 **87 次，其中 86 次一次补偿都没下发**——程序在不停地「介入 → 发现不对劲 → 退出 → 再介入」，但什么都没调成。

顺着日志挖到三条根因，前两个版本只是「绕开」了前两条，没有真正修掉：

### 根因 1：那台摄像头的「补偿」只能提亮，不能压暗

设备上报的能力范围是 `0 ~ +15`——**没有负值**。程序此前照样发「压暗 3 档」下去，设备会把负值一律钳成 0：指令发出去了，画面一动不动。此前的做法是「试两次发现没效果就换路」，代价是每件衣物都要先白试一次（约 4 秒）。

**现在**：只有设备真的报告了负值范围，才走硬件补偿；否则直接用下一档方案，不假装。

### 根因 2：切到手动档后，画面会崩到远低于请求的暗度

设备并不按它自己上报的曝光时间执行：自动模式下画面均值 203，切到手动后只剩 19（相当于压暗了 7.5 档，而程序一分钱都没要）。画面崩暗之后，「黑色衣物还在不在」的四道检测全部误判成「画面里没有衣物」，闭环既不下发补偿、也永远判断不出「这个档位无效」——于是每 3 秒循环一次「介入 → 崩 → 退出 → 再介入」。门店看到的「跳亮度」就是每次循环里手动/自动模式来回切。

**现在**：新增画面崩塌守卫——一旦帧亮度低于「本次请求所能解释的深度」，立刻还原曝光、改走软件压暗，并且**保持介入状态**（不再玩「退出等 3 秒再介入」的二次闪跳）。

### 根因 3：即使不崩，「介入了却一次都没调成」也没有出路

**现在**：这种情况会记入该设备的无效名单，连续两次后，后续衣物直接跳过这条走不通的硬件路径。

## 二、门店会观察到的变化

- **问题设备（HB-HD Camera 一类）**：徽标如实显示「**软件压暗 -x EV**」，而不是此前的「曝光补偿 -x EV」；**存档照片会真的被压暗**（此前徽标显示补偿档位、照片其实没压）；**预览画面不再变暗、也不再跳动**。
- **正常设备**：行为与 v1.2.14 完全一致，无感。
- 这一切都是自动的，**不需要任何操作**，覆盖安装即可。

重点验收（问题设备）：

1. 黑色衣物放上垫板 → 徽标显示「软件压暗」，照片里黑色衣物有纹理、白色鞋底不过曝；
2. 画面**不来回跳**，预览亮度稳定；
3. 把衣物拿走 → 约 3 秒后徽标消失、画面恢复正常；
4. 浅色衣物 → 不出现徽标；
5. 用手捂住镜头 → 仍然提示「画面异常（全黑）」且拍不了。

## 三、排查用日志

| 日志事件 / 字段 | 含义 | 怎么判 |
|---|---|---|
| `CAM_EXP_FALLBACK{reason:'frame-collapse'}` | 检出画面崩塌，已还原并降软件压暗 | 看 `refMean`（崩塌前帧均值）/ `rawMean`（崩塌帧均值）/ `floorMean`（容许下限）；`rawMean < floorMean` 即崩塌被实锤 |
| `CAM_EXP_RELEASE` 的 `gate` / `rawMean` / `subjRatio` / `adjusts` / `ghostStrike` | 退出时的闸门明细 | 衣物仍在画面却退出时，`gate` 告诉你是哪道闸没过、`adjusts=0` 说明整场一次没调成（配合 `ghostStrike` 看无效名单计数） |
| `CAM_EXP_OVERPRESS` | 设备实际压得比请求更深（v1.2.14 起） | 见 v1.2.14 说明；本版本的崩塌守卫不会把它误判成崩塌 |
| `CAM_EXP_STEP` | 每步曝光调整 | 看 `ev` 与 `subjectMean` 是否平稳收敛 |

若仍有异常，请把 `CAM_*` 日志导给我们。
