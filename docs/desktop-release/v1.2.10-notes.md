# 桌面端 v1.2.10 发布说明

**一句话**：本版是**画质修复版**——解决门店现场「摄像头拍出来的照片看不清衣物标签小字」：现在打开摄像头就拿 **该摄像头支持的最高分辨率**，并且这次选好的档位**下次打开还在**。

| 项目 | 值 |
|---|---|
| 版本 | v1.2.10 |
| 配套 | 移动端 **v1.1.0**（无需联动升级） |
| 上一版 | v1.2.9 |

---

## 一、这个版本解决了什么问题

多个门店反馈：**同一套系统，换一台电脑拍照清晰度就不一样**；同一台电脑重启之后，画面又变模糊了。具体到业务操作层面：

- 衣物条码标签、水洗标上的小字，拍照后放大是**糊的**，客户来取衣核对时看不清驳不倒；
- 明明在调试时调到了高清档，第二天开机又变回最模糊的那一档；
- 换了个 USB 口 / 换了个摄像头，清晰度再次回到最低档。

**真实原因是六个缺陷叠加**，不是某一处写错：

| # | 缺陷 | 现场表现 |
|---|---|---|
| 1 | 打开摄像头时**完全没有指定分辨率** | 摄像头直接落在驱动默认的**最低档**（常见 640×480） |
| 2 | 开流后用 `{ideal}` 提档 | `ideal` 只是「倾向值」，驱动可以完全无视，settings 原样不变 |
| 3 | 改用 `width.max × height.max` 拼组合 | 拼出驱动不支持的组合，被**静默吞掉**——不报错、不提档，界面无从察觉 |
| 4 | `applyConstraints` 超时分支**误判成功** | 从未生效的档位被当成「已锁定」，日志里一片正常 |
| 5 | 未与画面**真实尺寸**交叉校验 | settings 报着高清参数，实际出图仍是低分辨率 |
| 6 | 分辨率**没有存档** | 切设备 / 重启一律回落默认档，前一天调好的白调了 |

---

## 二、修复方案

### 1. 开流之前就锁定：一次到位

先把上一次成功锁定的档位读出来，以 **`exact`（硬性要求）** 直接写进 `getUserMedia` 约束里。摄像头一开流就是目标分辨率，不再依赖「开完再提」。

只有在**没有记忆**的时候（首次使用 / 换了新摄像头）才走候选阶梯探测。

### 2. 探测阶梯：面积优先，帧率次之

摄像头能力可以枚举出很多档位，按下面顺序排优先级逐个试探：

```
画面像素总数（面积）降序  →  帧率降序  →  宽度降序
```

在 `<video>` 拿到**第一帧之前**就完成试探和锁定，不会出现「先糊一下再跳清晰」的观感。

### 3. 失败不再含糊：三类降级原因说清楚

| 降级原因 | 含义 |
|---|---|
| `overconstrained` | 摄像头驱动明确表示支持不了这个档位 |
| `apply-timeout` | 该档位下发后超时未返回（部分 UVC 摄像头会「永不回应」） |
| `verify-mismatch` | 驱动说生效了，但**画面真实尺寸对不上** |

第三类正是上面「缺陷 #5」的护栏：**不再相信驱动自报的参数**，一律以 `<video>` 的实际画面尺寸为准。

### 4. 记忆按摄像头分别存档

锁定成功后才存档，且**按摄像头设备 ID 分开存**，换摄像头不会串档。存档带版本号与时间戳，写坏了、版本不认一律当作「没存过」并退回全量枚举——**绝不会被一条脏存档锁死**。

此前还有一个前置缺陷：**渲染层连「上次用的是哪个摄像头」都没记下来**，导致记忆档位无从匹配，一并修掉。

### 5. 兜底：不让用户干等黑屏

部分 UVC 摄像头每试探一个档位都要等到超时才返回。若不加限制，十几档下来「出画」要等十几秒——现场就是**黑屏 + 以为软件卡了**。

本版加了 **2.5 秒总预算闸门**（单一检查点统一收敛），超预算即刻以**当前已生效的档位**出画。**先出图，再谈画质**，绝不阻塞拍照。

## 三、这次是怎么验证的

本版**不是只靠读代码判断**：

- 分辨率阶梯排序、同分排名、边界档位逐一单测覆盖（98 + 102 项）；
- **变异对照**：人为把修复逻辑改回有 bug 的版本，确认 12 组断言**确实会失败**——确保「通过」不是因为检测失灵；
- **总预算闸门**专项验证（16 项），用恒挂设备模型确认出画不再被拖到十几秒；
- 自动化套件全部通过：门店、服务端、模板、水印、缩略图、凭据、摄像头（217 项）、摄像头日志（19 项）、摄像头质量（59 项）、确认队列（15 项）、本周订单导出（50 项）、手册渲染（75 项）、**发布隔离（红线）**；
- Electron **实机**验证：应用冒烟 105 项、界面布局 98 项，均在真实运行的桌面应用上执行。

## 四、兼容性

- **移动端保持 v1.1.0，不需要联动升级**：本版只改动桌面端摄像头取流逻辑与本地存档，未改动任何对外 HTTP 接口与数据格式。
- **已装 v1.2.9 可直接覆盖升级**，配置与照片数据不丢失。
- **已装更早版本**同样可直接覆盖安装到 v1.2.10。
- **首次升级的表现**：因为本版新增了分辨率存档，第一次打开时没有记忆，会走一次完整探测（约 1 秒内完成），之后打开即为上次的档位。

## 五、管理员操作指南（验证与回滚）

### 升级后建议这样验证

1. 覆盖安装 `xingqiyi-laundry-photo-setup-1.2.10.exe`；
2. 打开「衣物拍照」页面，**对准衣物标签上的小字**拍照，放大后应**清晰可辨**；
3. **完全退出并重新打开**应用，画面清晰度应与上次一致（**不再回落模糊档**）；
4. 若门店接了多个摄像头：切换到另一个摄像头再切回来，两边的档位应各自保持、**不互相串档**；
5. 观察从点开拍照页到出画的时间，应在 **1 秒左右**，不应出现长时间黑屏。

### 回滚

若发现异常，覆盖安装上一版 `xingqiyi-laundry-photo-setup-1.2.9.exe` 即可。**必须整包覆盖安装，不要只替换单个文件**。

---

## 六、安装

双击 `xingqiyi-laundry-photo-setup-1.2.10.exe`，按向导完成安装（可自选目录）。安装包内置全部运行环境，目标电脑无需安装 Node.js。

安装包 SHA-256 校验值由发布流程自动生成，见发布附件 `SHA256SUMS.txt`。

## 七、已知未修（后续版本处理）

- 部分驱动会把同一分辨率按不同帧率重复上报，探测阶梯会依次试探它们；已由总预算闸门兜住时延，但首次探测的次数仍略多于理论最小值。
- 摄像头若在应用运行中「被拔出再插回」，会以最后记忆的档位重开；极少数驱动在热插拔后会临时拒绝该档位，此时会降级到次优档并在下次冷启动时重新提档。
